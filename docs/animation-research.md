# Character animation: research and current limitations

## Sources reviewed

- [OpenBone](https://github.com/UXCentury/open-bone): MIT-licensed editor and runtimes; documents weighted meshes, physics constraints, layers, and a PixiJS integration. It requires an authored rig and assets; it does not turn a flattened pose into separate limbs or faces automatically. A standalone browser smoke test with its sample Button document and the game’s PixiJS 8.23.0 rendered one draw call successfully; actual character rigs, physics, mobile performance and integration remain untested.
- [Untitled Pixi Live2D Engine](https://github.com/Untitled-Story/untitled-pixi-live2d-engine): an MIT PixiJS v8 integration for Cubism models, requiring the separate Cubism runtime and a prepared model. Check Cubism's own licensing before distribution; the plugin's MIT license is not a license for Cubism Core or third-party models.
- [DragonBones Pixi runtime](https://github.com/FlySkyPie/dragonbones-pixi): MIT, but its README targets PixiJS 4, not this game's PixiJS 8. It would need compatibility work and an authored rig.
- [wobble](https://github.com/skevy/wobble): describes a closed-form damped harmonic oscillator for spring animation. An exponentially damped sine can serve as an art-directed secondary response; it is not a biomedical model of anatomy.

## Current implementation

All 30 currently shipped plates have hand-located torso and leg regions in `src/heroine/poseAnatomy.ts`, measured against the actual game assets. The two rear-view bikini poses use hips rather than a front chest region. A short damped response follows the target region after a tap, with intensity increasing across days. Breathing uses the torso, except for rear-facing poses where it uses the back. The chair remains part of the same flattened texture: conservative interior meshes reduce collateral motion, but are not a proof that every chair pixel is unaffected. The movement is a localized deformation, not independently articulated body parts, true limb movement or frame-by-frame animation.

First- and second-day facial patches exist. Most later plates deliberately suppress those patches because their painted faces, angles, costumes and occlusions do not match the first-day overlays. True per-pose expression/blink layers and premium articulation need authored, registered assets and occlusion handling. In particular the approved static originals must be retained and any reconstruction of hidden body/chair portions needs visual review and approval.

## Next steps for premium animation

1. Prototype one representative pose as a layered rig, including separate chair, hair, body, outfit, limbs, eyes and mouth; reconstruct only occluded backing pixels on working copies, keeping approved originals intact.
2. Validate import and PixiJS 8 playback, asset and runtime licenses, mobile performance, reduced motion, repeat taps and layer seams before choosing a runtime.
3. Have the user evaluate a visual playback before producing the other 29 rigs; author actual pose-specific joint and secondary motion, and expression shapes separately rather than pasting the Day-1 face onto different art.
4. Check chair response only when physically justified by contact, and inspect actual chair pixels, not merely a bounding-box proxy. Avoid assigning physics to objects held in fixed hands unless the pose provides appropriately rigged hand/prop layers.

## Further investigation: from a flat image to an animated character

These are separate steps: (1) extract and complete overlapping artwork layers, (2) author a rig and motions, and (3) play it inside the game. None of these sources proves that a complex seated pose will work automatically or preserve the approved image pixel-for-pixel.

### Layer extraction and occluded areas

- [See-through](https://github.com/shitagaki-lab/see-through) is a SIGGRAPH 2026 research project for decomposing one anime illustration into depth-ordered, inpainted semantic layers and exporting PSD; it reports up to 23 layers. It is the most relevant starting point, not a finished animation or guaranteed separation of chair, hands, props and individual limbs. Inspect the flattened PSD against the source, and manually repair seams and reconstructed areas. Its repository describes roughly 12–16 GB VRAM at 1280 resolution by default, or around 10 GB with group offload. A [hands-on setup article](https://lilting.ch/en/articles/see-through-anime-layer-decomposition) reports roughly 14 GB of model downloads. This sandbox has no visible NVIDIA GPU and lacks the required PyTorch runtime; no inference on the user’s artwork has been performed.
- The [public demo](https://24yearsold-see-through-demo.hf.space/) runs on a third-party service, with lower suggested resolution and quotas/timeouts. Do not upload the user's art without explicit permission; review its privacy and output terms first.
- See-through's code is Apache-2.0, but model weights have additional upstream terms. The maintainer's [license clarification](https://github.com/shitagaki-lab/see-through/issues/43) says commercial use is permitted, while LayerDiff and depth models carry Open RAIL restrictions, including terms-of-use obligations for services; body-parsing weights are Apache-2.0. Check the current model cards, licenses and intended usage independently before production; the issue remains open.
- [Anime Face Segmentation](https://github.com/siyeong0/Anime-Face-Segmentation) can assist with visible facial masks, not reconstruct hidden regions or create new expressions.
- [anime-part-split](https://huggingface.co/tsunehimatoi/anime-part-split) restricts usage to research/personal non-commercial use; unsuitable for commercial release without separate permission.

### Rigging and playback

- [Stretchy Studio](https://github.com/MangoLion/stretchystudio) (MIT) advertises See-through PSD import, automated rigging via DWPose or heuristics, meshes and shape keys. Promising for a first editable rig, but its export and interoperability with a chosen game runtime need verification, as do separately distributed model dependencies.
- [2DAutoRigger](https://github.com/matbn/2DAutoRigger) describes slicing, refinement, rigging and export. Core code is Apache-2.0, but plugins/models have separate licenses. Its quality and handling of overlapping seated poses are unverified.
- [image2live2d](https://github.com/Wzhang3912/image2live2d) converts already separated PSD/PNG layers into rigs; a flat input still requires the decomposition stage. Check each output/runtime and dependency license, especially for Cubism.
- [Rigby2D](https://github.com/jaisurya-dev-art/rigby2d) describes PSD import, weighted meshes, IK, physics and a Pixi 8 runtime; promising but early-stage and not tested here.
- [OpenBone Pixi](https://github.com/UXCentury/open-bone/tree/main/packages/pixi) publishes `@openbone/pixi` with PixiJS `^8.0.0` as a peer dependency. An isolated, non-production Playwright smoke test loaded and rendered its sample `button.obone` with `@openbone/pixi` 0.4.6 and PixiJS 8.23.0. This establishes only basic sample loading/rendering, not a successful PSD import, character animation, physics, or performance in this game. No dependency was added to the project.
- [Live2D physics tutorial](https://www.youtube.com/watch?v=kTbhZQ7AVwg) is a practical rigging reference; authored layers, motion tuning and runtime rights remain separate considerations.

### Recommended experiment

Try one representative pose on a working copy: See-through extraction on a suitable GPU (or a privacy-approved service), manually correct chair/body/limb/prop separation and hidden pixels; evaluate Stretchy Studio and whether its export can actually be brought into OpenBone or Rigby2D. If not, author/import the corrected layers directly in the selected rig editor. Test idle breathing, tap, expression and hand/prop/foot motion visually against the original, including chair contact and seams. Only after a successful sample should the remaining 29 poses be costed and built. The current mesh approach is still in place; none of these external tools has been integrated into the game.

### Additional lead: Mesh Avatar Studio

[Mesh Avatar Studio](https://github.com/shinshin86/mesh-avatar-studio) is an MIT-licensed editor and mesh-avatar workflow that documents agent-assisted manual layer cutting, coordinate checks and visual motion review. It recommends transparent, front-facing head-and-shoulders art; full-body seated characters and integration into Pixi have not been validated. Its optional expression-generation workflow sends art to an external provider and requires consent. Its documented agent recommendations do not mean those other agents or models are available in this session. This is a lead to test rather than a proven automatic conversion.

### Isolated motion lab

`experiments/animation-lab` is a separate preview for one copy of the approved day-six starting plate. It compares still and moving art and offers breathing, torso/leg impulses, repeat and a strength control. It uses a fine Pixi mesh, not See-through, OpenBone or a real layered rig; the chair is baked into the source so isolation is not guaranteed. No game code or original artwork was changed. A browser smoke test checked both impulses and reduced motion; subjective visual quality and chair edges still require review. Run with `cd experiments/animation-lab && ../../node_modules/.bin/vite --host 0.0.0.0 --port 5186` after installing the project's dependencies.

### GitHub tooling investigation and local tests

- [Anime2.5DRig](https://github.com/852wa/Anime2.5DRig) is MIT-licensed and describes client-side PSD parsing, automatic rigging, mesh warp and spring motion. See-through lists it as a community tool compatible with its layer naming. Cloned separately under ignored `.qa-out`, ran `npm test`: its Node rigger/runtime/face/PSD suites passed (including its own 17- and 20-part example PSDs) and 9 Python tests passed. This does not test our art, Pixi integration, or Safari/iPhone; it requires pre-separated PSD. Check third-party dependencies and any external network calls before deploying.
- [Mesh Avatar Studio](https://github.com/shinshin86/mesh-avatar-studio) was cloned separately and `npm ci --ignore-scripts` completed. Its `npm run doctor` reported Node and packages present, but `uv` and its own Playwright Chromium missing; rig generation and motion-review workflow not run. npm reported 12 dependency vulnerabilities (8 moderate, 2 high, 2 critical); audit remediation and security review required before deployment. Its workflow requires careful manual facial coordinate placement and is optimised for head-and-shoulders, so chair/legs/props are not demonstrated.
- The interactive motion lab is served as an Arena preview with an iPhone-sized layout; it uses the actual approved image copy and does not use or demonstrate either GitHub tool. Browser checks used desktop Chromium and an emulated mobile viewport, not actual iPhone Safari. The preserved game baseline is commit `1009a58`; subsequent changes are isolated to the experimental lab and research notes.

### Forearm-and-prop layer experiment

`experiments/layered-arm` is an isolated, manually cut copy of the approved day-six opening plate, with a forearm and cucumber rotating together about an approximate elbow pivot. OpenCV Telea fills the backing under the cut locally, so reconstructed hidden areas are guesses. Inspection of the cut layer shows it also contains chair, hair and shoulder pixels; it is not clean separation and cannot yet be accepted for integration. The original still is shown at rest; an amplitude and loop control let the user inspect motion. Test in desktop Chromium and touch-emulated 390px viewport checked impulse, repeat, reduced motion and no horizontal overflow; real iPhone Safari and visual quality are unverified. The actual source art remains unchanged; all derivative files are confined to the experiment.

As an additional input check (not a runtime or visual test), Anime2.5DRig's `buildRig` was fed these two RGBA layers locally. It processed two layers but warned that no face/eye/mouth layers exist, and treated the unknown arm layer as head-following. This demonstrates that this crude split is not a usable automatic rig; the library does not infer an elbow/prop rig from the two layers. Proper segmentation, semantic naming and an appropriate full-body rig are still necessary.

### Mask refinement experiment

`experiments/layered-arm-refined` applies OpenCV GrabCut (color-based foreground/background segmentation) to the first arm study, plus manually drawn exclusion boundaries; this removes much of the chair/hair previously present in the moving layer. The segmentation still has imperfections near the upper arm and thin outlines. In particular the locally inpainted background contains blurred chair/skin and a residual green fragment, so large motion reveals artefacts; this is not production-ready. The original image remains byte-identical to the shipped source. `deliverables/test_mii_ruka_v2.gif` captures the actual Pixi experiment, 24 timed samples, at a 4-degree setting. Reduced-motion behavior and page errors were checked in Chromium, not on iPhone Safari.

Research references: [GrabCut article](https://www.louisbouchard.ai/grabcut-notebook-implementation/) and [iterative GrabCut](https://github.com/louisfb01/iterative-grabcut) (MIT) describe iterative foreground/background corrections, not automated occlusion recovery. [AnimeSeg](https://github.com/suzukimain/AnimeSeg) is a potential anime semantic-segmentation lead, but its GitHub metadata did not report a license and its models require separate checks; it was not run here. [See-through paper](https://dl.acm.org/doi/10.1145/3799902.3811209) targets completion of occluded regions, which classical visible-pixel segmentation does not provide; its GPU pipeline remains untested here. None is a proven solution for this seated chair/prop composition.

### Resolution test and prompt research

- The earlier arm GIF was only 380×570 pixels, so it could not faithfully show the art's native detail. The approved day-five source is 1664×2496 and the game plate is 1024×1526; upscaling a low-resolution preview cannot restore lost detail.
- `experiments/highres-bikini/animation_reference.png` is a newly generated, separate animation study, **843×1264**, not an approved replacement or higher resolution than the earlier approved day-five source. The first and another requested camera-angle generation were blocked; the accepted image is a less foreshortened beach-chair composition with feet down, not the requested soles toward camera. Keep it out of the game until approved.
- `deliverables/test_bikini_breath.gif` and `deliverables/test_bikini_breath_full.png` (APNG) are a 20-frame breathing mesh/warp test at the new source's full 843×1264 resolution. APNG preserves full RGB, GIF uses a restricted palette. Both are looping experiments; the movement is a torso-local pixel warp, not articulated body parts or facial animation. APNG frame comparison at peak yielded a changed bounding box (316,323)-(523,446) while the left chair area x<270 stayed identical; this is a targeted pixel check, not complete perceptual or physical validation. Browser/viewer playback of APNG on an actual iPhone has not been verified.
- [Character prompting guide](https://github.com/userzz1145141919810-rgb/gpt-image-2-5-prompting-guide) recommends explicitly stating reference roles, spatial relationships, camera framing and identity locks; these are general suggestions, not a guarantee of a certain model, exact dimensions or a faithful result. [Arena's image documentation](https://help.arena.ai/articles/5595418316-arena-how-to-file-upload) describes uploading visual references, but does not promise controllable native dimensions or provide bypasses for moderation. For animation, source art, visible masks, occluded-region completion, rigging, and review are distinct steps.

### Local high-resolution investigation (Real-CUGAN ONNX)

- [Real-CUGAN ONNX Web](https://github.com/Hoshino-Yumetsuki/realcugan-onnx-web) distributes ONNX variants; it is a client-side upscaler, not an image generator. It and [original Real-CUGAN](https://github.com/bilibili/ailab/tree/main/Real-CUGAN) publish MIT licenses for their respective code; check all weight provenance/terms before production distribution. It was cloned only into ignored `.qa-out`, not added as a dependency or deployed. Model tested: `weights_v3/up4x-latest-conservative.onnx`, SHA256 `1e79465f6556aa2893c8af3f35d19781341c529fcd7a949b54bb282a8a58b5f7`. ONNX Runtime 1.32 CPU, 2 threads, 128px tiles with 32px context. `experiments/upscale/realcugan_onnx.py` is the isolated reproducible runner; it requires a separately obtained model and supports opaque RGB images only.
- Generated art `native_quality_candidate.png` was requested at approximately 1664×2496 but returned 848×1264; no native-size control is exposed in the generation tool. Prompting dimensions did not guarantee output size. It is a separate unapproved studio test and not the requested feet-facing-camera pose. No game asset was replaced.
- Successfully upscaled this candidate locally to `deliverables/mia_studio_test_4x.png` (3392×5056); another beach image was upscaled from 843×1264 to `deliverables/mia_bikini_ai_upscale_4x.png` (3372×5056). This is AI super-resolution, **not native 5K generation**. It visibly sharpens and simplifies lines/texture, which may change art details or erase fine blush lines. Both source images are retained. See `deliverables/sravnenie_studio.png` and `deliverables/sravnenie_kachestva.png` for matching Lanczos comparisons. No original artwork was modified or uploaded.
- Tested a 256×256 face region with tiled vs untiled inference: mean absolute difference 0.32/255, maximum 11.6/255, 0.05% of RGB samples over 5/255; this is not proof all image seams are invisible. Animated-frame temporal stability and model rights for commercial release still need separate tests.
- [Real-ESRGAN](https://github.com/xinntao/Real-ESRGAN) has an anime-oriented model and CPU-capable implementations; not tested here. [ComfyUI tiled diffusion](https://github.com/shiimizu/ComfyUI-TiledDiffusion) and [Ultimate SD Upscale](https://github.com/ssitu/ComfyUI_UltimateSDUpscale) are generative alternatives that can create new details but risk identity drift and seams; GPU/model dependencies and output licenses need review. They have not been run here. [MiniMax-H3-Image](https://github.com/MiniMax-AI/MiniMax-H3-Image) documents explicit image-size parameters on a different stack; the model has separate terms, resource and API-access requirements and is not available through the current generation tool. Do not assume it or any prompt will override service moderation or guarantee quality.

### Follow-up: transparent game plates, animation and generation tooling

The runtime currently preloads the day ladders together. A single 4096×6104 RGBA texture is ~95 MiB decoded, so thirty-two full-resolution textures would be approximately 3 GiB before other GPU resources; indiscriminate replacement risks mobile crashes. The original 1024×1526 plates are also the coordinate system for meshes, hits and face patches. Therefore the `rgba_realcugan.py` pilot is non-destructive: x4 RGB inference on a colour-extended transparent source, then independently resampled alpha; an optional proof reattaches the exact original alpha at 1024×1526. Original full 4x outputs go to `deliverables/game-upscale/`; this is a processing queue, not a declaration that every frame is approved or loaded in the game. Edge extension and independent alpha can still generate halos and distort details; inspect all compositions, seams, hand, face and edge patches before promotion. The master images are 4096×6104 (AI enlarged, not native generated 5K). Identity and source artwork remain available in Git. Production requires a memory-bounded lazy texture loader and scaling of the mesh and face coordinates; actual iOS hardware QA is needed.

The game's tap-only region gains 20% for `chest` targets on front-facing regions marked `chest`; covered poses, hip/back regions, leg taps and breathing retain prior strength. This is a shared-image mesh warp and numerical coverage does not prove a chair, hands or props are immobile; visual pose-by-pose QA remains necessary.

[See-through](https://github.com/shitagaki-lab/see-through) generates semantic PSD layers but not a complete animation rig; GPU and weights are required and this scene has not been run. [Stretchy Studio](https://github.com/MangoLion/stretchystudio) accepts layered art and supports mesh and joint ideas; [Anime2.5DRig](https://github.com/852wa/Anime2.5DRig) offers an editor, blink/lip sync, face anchors and hair physics on suitable PSD layers; only its sample tests were run here. Our previous GrabCut arm experiment revealed occluded-background artifacts, not a finished limb. For hands holding props, create forearm, hand and held object with connected pivots and painted-in background; for legs/feet provide upper/lower leg and foot plus occluded seat; for face author matched eye-open/closed, brows and mouth alternatives. Contact points and perspective must be manually reviewed for each pose. No automatic system tested here guarantees this or preserves the chair.

[ComfyUI](https://github.com/Comfy-Org/ComfyUI) is a node-based runtime, not an included checkpoint; [comfyui-auto-anime-prompts](https://github.com/jluo-github/comfyui-auto-anime-prompts) provides structured prompt-node inspiration. `experiments/prompt-lab/` is an offline Python prompt and ComfyUI API graph builder, not an image generator: no ComfyUI, generative checkpoint, GPU or generated output is supplied. It does not bypass model/provider restrictions and does not guarantee character identity, composition or anatomy. Check each checkpoint and tool's separate licenses before commercial use.

#### Batch result

The batch completed for the 30 stage plates plus two flash plates in `experiments/upscale/game-plates.txt`. All 32 master images were decoded at 4096×6104 and all 32 game-size proofs had 1024×1526 dimensions and byte-identical alpha channels to the original plates. `experiments/upscale/game-manifest.json` contains the original plate and output hashes. The 4x RGB inference was applied to the already prepared 1024×1526 game assets, not the original 1664–2528px art-studio masters. The enhanced RGB was resized back to 1024×1526 for the game (same layout and GPU size, not 5K runtime), with the original alpha reattached. The original game files remain recoverable from Git commit `9870f1d`. Full-size AI masters are in `deliverables/game-upscale/`; do not preload them all in Pixi. Restore source originals to a separate directory and set `SOURCE_DIR` and `MODEL` to use the resumable batch runner; do not run it against enhanced runtime plates.

All 58 existing Node tests and the full numerical Playwright test of thirty poses/two tap zones plus reduced motion passed locally after replacement. Playwright mobile Chromium loaded the Day 5 opener and chest response without JS exceptions; actual iPhone Safari and detailed visual review of all animation at every pose remain outstanding. `qa_day2_mobile.mjs` timed out waiting for the disabled/hidden start-day-2 button, so the end-to-end mobile day transition is not confirmed by that script. Numerical checks don't prove each mesh's pixels are anatomically correct or that the entire chair is unchanged.
